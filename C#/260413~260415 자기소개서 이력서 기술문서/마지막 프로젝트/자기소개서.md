## 1. 업적 시스템, 리팩토링

### 개요
- 플레이어의 게임 진행 상황(재화, 레벨, 플레이타임 등)을 감지하여 성과를 보상하는 업적 시스템을 구현하였습니다. 기존의 비효율적인 검사 방식을 개선하고, 확장성과 성능을 고려하여 옵저버 패턴을 적용한 재설계를 진행했습니다.

### 개선 사항
1. 순회 방식의 최적화 (폴링 -> 이벤트 기반)
   - 기존의 방식은 일정 시간마다 업적 시스템이 모든 업적 항목을 순회하면서 상태를 확인하는 방식이었다. 이 방식은 업적 개수가 늘어날수록 연산 부하가 기하급수적으로 증가하는 문제가 있었습니다.
2. 이 문제를 해결하기 위해서 특정 상황 발생 시에만 동작하는 이벤트 기반 옵저버 패턴으로 전환하여 불필요한 연산을 제거하였습니다.

## 2. 직원 시스템 

 게임 특성상 직원매니저에 모든 기능을 넣는다고 생각하면 갓 오브젝트가 될 가능성이 있었습니다. 그 상황을 피하기 위해 직원을 관리하기 위해 Employee-EmployeeList-HaveEmployee-EmployeeManager 등등 계층을 나눠 각 계층에 맞는 객체만 관리하게 하여 책임분리를 확실하게 하였다.  

### EmployeeList: 전체 직원 프리팹 및 고용되지 않은 대기자 풀을 관리하는 데이터 저장소 

### HaveEmployees: 현재 입사한 직원들의 상태(대기/프로젝트/교육)별 리스트를 동기화하고 유지하는 상태 관리자 

### Employee: 직원 개별 데이터와 능력치 변화 로직을 캡슐화한 단위 객체 

 

## 3. 튜토리얼 시스템 

트러블 슈팅 과정 

씬 참조 방식 -> 처음에는 화면 전체를 패널로 덮고 활성화 해야할 객체만 씬에서 참조해서 넣는 방식, 문제점 : 씬에 존재하지 않는 객체가 있다. 

펀치홀 방식 -> 두번째 방법 패널을 다 덮고 그 패널에 구멍을 뚫어서 오브젝트와 상호작용 가능하게 하는 방식 문제점 : 유저에게 특정 버튼을 누르게 하도록 유도할때 어떤 버튼을 눌러야 하는지 햇갈릴 수 있는 경우가 있음. 

Id 태그 방식 -> 세번째 방법 : 오브젝트가 생성될 때 아이디를 달고 시작하게해 그 오브젝트만 활성화되게 하는 방법, 문제점 : 한가지 종류의 객체가 여러개 생성될 때 그 순서를 에측할 수 없음 

통합 Enum 기반 매니저 패턴  -> 네번째 방법 : 위의 방법을 모두 모아 Enum으로 모아두어서 각각 필요한 상황에 쓸 수 있도록 하게함. 
 
```c#
public enum ShowMode 
{ 
   TextOnly, 
   ButtonActivated, 
   HighlightSqureTouchAnywhere, 
   HighLightSqureTouchSomewhere, 
   PunchHole, 
} 
```
